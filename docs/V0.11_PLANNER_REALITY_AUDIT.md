# V0.11_PLANNER_REALITY_AUDIT.md — Unflinching Audit of the v0.11 Planner

> **Milestone**: AstraRun v0.11.1  
> **Audited Target**: `astrarun.agent.planner`, `astrarun.agent.loop`, `astrarun.agent.graph`, `CapabilityRegistry`, `AstraApplication.handle_request`  
> **Status**: COMPLETED  
> **Date**: 2026-09-29  

---

## 1. Executive Summary: Intent Switch vs. Genuine Agent

In v0.11, AstraRun introduced foundational agent runtime primitives:
- `Goal` and `Plan` dataclasses (`astrarun.agent.models`)
- `ExecutionGraph` DAG engine with Kahn's topological sort (`astrarun.agent.graph`)
- `AgentExecutionEngine` with closed-loop ACT -> OBSERVE -> VERIFY (`astrarun.agent.loop`)
- `ResourceLockManager` workstation concurrency locking (`astrarun.agent.locking`)
- Live Task HUD V2 with non-focus-stealing flags (`WS_EX_NOACTIVATE`) and `TaskETAEstimator`

However, an exhaustive audit of the decision and planning paths reveals:
> **The v0.11 planner was NOT a general dynamic agent. It was an explicit intent switch wrapped inside agent abstractions.**

The runtime could execute DAGs, but the DAGs themselves were hardcoded by rigid regex and if/elif statements inside `planner.py`.

## 2. Explicit Audit Questions (A through J)

### A. How does the planner determine a goal?
In `GoalPlanner.parse_goal(raw_prompt)` (`src/astrarun/agent/planner.py`, lines 35–96):
The prompt is checked against a sequence of hardcoded regular expressions:
```python
if re.search(r"\bbattery\s+report\b", clean, re.IGNORECASE):
    goal.intent = "generate_battery_report"
    ...
elif wifi_conn_match ...:
    goal.intent = "wifi_connect"
elif re.search(r"\b(?:disconnect|turn off)\s+(?:from\s+)?wifi\b", ...):
    goal.intent = "wifi_disconnect"
elif re.search(r"\b(?:scan|list|find|show)\s+(?:available\s+)?wifi\b|\bwifi\s+scan\b", ...):
    goal.intent = "wifi_scan"
elif re.search(r"\b(?:check|show|get)?\s*wifi\s*(?:status|state|connection)?\b", ...):
    goal.intent = "wifi_status"
elif re.search(r"\b(?:check|get|show)\s+battery(?:\s+status)?\b", ...):
    goal.intent = "battery_status"
else:
    goal.intent = "composite_workflow"
```
Furthermore, in `AstraApplication.handle_request` (`src/astrarun/app.py`, lines 431–432), the agent engine is **only** called if the request matches `battery report` or `wifi`:
```python
if re.search(r"\bbattery\s+report\b", clean, re.IGNORECASE) or re.search(r"\b(?:scan|check|show|connect|disconnect).*wifi\b|\bwifi\b", clean, re.IGNORECASE):
    agent_task = self.agent_engine.execute_goal(clean)
```
Any other prompt is intercepted by the legacy router or fast paths before the agent runtime is ever reached.

### B. How does it choose capabilities?
In `GoalPlanner.create_plan(goal)` (`src/astrarun/agent/planner.py`, lines 98–191):
Capabilities are assigned through explicit string equality branches:
- `if intent == "generate_battery_report":` -> `step.capability_id = "generate_battery_report"`
- `elif intent == "wifi_scan":` -> `step.capability_id = "wifi_scan"`
- `elif intent == "wifi_status":` -> `step.capability_id = "wifi_status"`
- `elif intent == "wifi_connect":` -> `step.capability_id = "wifi_connect"`
- `elif intent == "wifi_disconnect":` -> `step.capability_id = "wifi_disconnect"`
- `elif intent == "battery_status":` -> `step.capability_id = "battery_status"`
- `else: plan = self._decompose_composite_prompt(goal)`
Inside `_decompose_composite_prompt`:
- `open ... and type ...` -> creates 2 hardcoded steps: `open_application` and `type_into_window`
- `open ...` -> creates 1 step: `open_application`
- `snap ...` -> creates 1 step: `snap_window`
- fallback -> creates 1 step: `system_summary`

No capability schema or registry metadata is queried during planning. Capabilities are selected via static string literals.

---

### C. Are capability IDs manually selected through if, elif, regex, or keyword branches?
**YES.** 100% of capability IDs in `GoalPlanner` are manually written in `if/elif` branches and regex match blocks. There is zero dynamic retrieval.

---

### D. How many user goals have explicit hardcoded handling?
Exactly **9** specific intent forms:
1. Battery report generation (`generate_battery_report`)
2. Wi-Fi scan (`wifi_scan`)
3. Wi-Fi status (`wifi_status`)
4. Wi-Fi connect (`wifi_connect`)
5. Wi-Fi disconnect (`wifi_disconnect`)
6. Battery status (`battery_status`)
7. Open app + type text (`open_application` + `type_into_window`)
8. Open app (`open_application`)
9. Snap window (`snap_window`)

All other inputs collapse to the default single step (`system_summary`).

---

### E. Can the planner use a newly registered capability WITHOUT modifying planner.py?
**NO.** If a new capability `reverse_text` is registered in `CapabilityRegistry`, `GoalPlanner` does not know it exists. Calling `planner.parse_goal("reverse hello world")` classifies it as `composite_workflow` and produces a plan executing `system_summary`.

---

### F. Can it combine capabilities in an ordering that was never explicitly programmed?
**NO.** The only multi-step plan in v0.11 is the hardcoded two-step sequence: `open_application` -> `type_into_window`. The planner cannot compose novel sequences (such as `wifi_scan` -> `wifi_connect`, or `find_latest_file` -> `open_file`).

---

### G. Can it use capability outputs as arguments to later capabilities?
**PARTIALLY SUPPORTED IN THE GRAPH, UNUSED BY THE PLANNER.**
`ExecutionGraph._propagate_data` supports copying fields via `dep.data_mapping`:
```python
for out_key, in_arg in dep.data_mapping.items():
    if out_key in dep_step.result.data:
        step.arguments[in_arg] = dep_step.result.data[out_key]
```
However:
1. `GoalPlanner` never populates `data_mapping` dynamically.
2. There is no symbolic representation (`${step1.field}` or `OutputReference`).
3. Output-to-input binding cannot be expressed in user goals.

---

### H. Can it replan after an unexpected observation?
**NO IN PRACTICE.**
In `AgentExecutionEngine._attempt_replan` (`src/astrarun/agent/loop.py`, lines 259–279):
```python
if failed_step.capability_id == "type_into_window" and failed_step.interaction_tier == InteractionTier.TIER_C_UI_AUTOMATION:
    failed_step.interaction_tier = InteractionTier.TIER_D_INPUT_EMULATION
    failed_step.state = StepState.PENDING
    failed_step.retry_count = 0
    task.replans.append(replan_event)
    return True
return False
```
This is a **tier degradation fallback** for a single capability (`type_into_window`), not replanning. The graph is never restructured, no alternate capabilities are retrieved, and any other failed step results in immediate task failure.

---

### I. Can it discover that its original plan was insufficient?
**NO.** The engine executes the steps in the DAG until terminal states are reached. If all steps return success, the task is marked `COMPLETED`. There is no `GoalVerifier` evaluating whether the user's high-level goal was actually achieved (e.g. verifying an expected file was created at the right path with non-zero size, or verifying the network actually switched).

---

### J. Can it construct a task containing 5–10 steps without a predefined workflow template?
**NO.** The planner has no multi-step search or decomposition engine. Plans are either 1 step or 2 hardcoded steps. Constructing a 5–10 step plan dynamically from capability schemas is impossible in v0.11.

## 3. Architecture Roadmap for v0.11.1

To transform AstraRun from an intent switch into a true autonomous workstation agent, v0.11.1 will implement:

1. **`CapabilitySemanticIndex`**: Searchable semantic index across all 77+ capabilities (verbs, nouns, domains, examples, inputs, outputs, prerequisites) with top-K retrieval.
2. **Dynamic Capability Planning**: Discovers and constructs valid DAGs from capability schemas without modifying `planner.py`.
3. **Symbolic Dataflow (`OutputReference`)**: Explicit `OutputReference(step_id, field)` and `${step1.field}` resolving dynamically through graph data propagation.
4. **General Dataflow DAG**: Parallel branches (e.g. `cpu_metrics` + `memory_metrics` -> `compose_summary` -> `save_file`).
5. **Typed Plan Validation (`PlanQualityValidator`)**: Pre-execution verification of cycles, dangling references, required arguments, and risk policies.
6. **Goal Completion Verification (`GoalVerifier`)**: Independent post-plan empirical validation that the user goal was achieved.
7. **Real Dynamic Replanning (`PlanRevision`)**: If an action fails and observation reveals an alternative, the DAG is dynamically revised, recorded in `PlanRevision` history, and safe execution resumes.
8. **Typed Observations & Freshness TTL**: Machine observations with explicit TTLs preventing stale actuation.
9. **Dynamic Argument Provenance (`ArgumentBinding`)**: Explicit tracking of parameter values from user text, entity resolvers, context, previous steps, or observations.
10. **The Critical Plug-In Test**: Proves a newly registered capability (`reverse_text`, `save_text_file`) is discovered and composed without changing `planner.py`.
