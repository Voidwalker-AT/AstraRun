> **Document Type**: Architecture & Security Research Specification  
> **Target System**: AstraRun Dynamic Tool Execution Runtime  
> **Status**: APPROVED (C1 Reality Baseline)  
> **Date**: October 2026  
> **Classification**: `CONTAINED_EXECUTION_NOT_FULL_SECURITY_SANDBOX`

## 1. Executive Summary & Problem Statement

Prior AstraRun documentation referred to `SandboxManager` as a "secure sandbox". The independent product reality audit revealed that `SandboxManager` relies exclusively on **Win32 Job Objects** (`CreateJobObjectW`, `SetInformationJobObject`, `AssignProcessToJobObject`).

While Win32 Job Objects are vital for workstation stability, they provide:
- **PROCESS CONTAINMENT** (Memory quotas, CPU rate limits, timeout enforcement, kill-on-job-close, suppression of console windows).
- **NOT SECURITY ISOLATION** (Processes execute under the host interactive user token and inherit full ambient user privileges to the filesystem, network, registry, and Windows API).

Labeling Job Objects as a security sandbox is misleading. AstraRun explicitly classifies its current runtime security state as:
```
CONTAINED_EXECUTION_NOT_FULL_SECURITY_SANDBOX
```

Generated code must not be allowed to act with unconstrained host credentials. This document defines the active defensive layers enforced in Phase C1 and evaluates the Windows-native architectural roadmap for achieving true zero-trust execution boundaries in subsequent milestones.

## 2. Active C1 Defensive Perimeter

In Phase C1, security does not rely on process virtualization alone. Instead, a multi-stage defense-in-depth perimeter intercepts and constrains dynamic code before, during, and after execution:

### 2.1 Layer 1: Static AST Screening (`ASTInspector`)
Before any code generated by Qwen is submitted to the interpreter:
- **Abstract Syntax Tree Parsing**: Parses code via Python standard `ast`.
- **Forbidden Module Whitelisting**: Prohibits imports of `subprocess`, `ctypes`, `winreg`, `socket`, `urllib.request`, `requests`, and raw C-extension loaders unless explicitly declared and approved.
- **Forbidden Builtins**: Detects and rejects `eval()`, `exec()`, `compile()`, `__import__()`, and `open()` with absolute paths outside the designated workspace.
- **AST Repair Loop**: In case of non-critical violations (e.g., interactive GUI plotting instead of headless Agg backend), requests automated bounded repair from Qwen (up to 2 iterations).

### 2.2 Layer 2: Authoritative Security Broker (`ExecutionBroker` & `ActionGate`)
- All consequential capabilities pass through `ExecutionBroker.execute(ActionProposal)`.
- Models never execute Python interpreters directly.
- Actions are classified into `ACT` vs `OBSERVE` to prevent confirmation fatigue on read-only queries while strictly governing file mutations and script synthesis.

### 2.3 Layer 3: Environment Scrubbing & Secret Sanitization
- Child processes do NOT inherit parent API keys, browser cookies, SSH credentials, or environment secrets.
- `ASTRARUN_*` internal state tokens and secret brokers are scrubbed from the spawned child process environment.

### 2.4 Layer 4: Job Object Resource Containment (`SandboxManager`)
- Limits maximum committed virtual memory per process to 512 MB (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`).
- Limits active execution duration (e.g. 30–60 seconds) with forced asynchronous termination.
- Ensures orphan child processes cannot linger in background (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`).

## 3. Windows-Native Security Isolation Roadmap

To advance beyond process containment without requiring heavyweight hypervisors or degrading sub-second launcher responsiveness, the following Windows-native isolation technologies are evaluated:

| Isolation Technology | Security Boundary | Setup Latency | Resource Overhead | Workstation Feasibility | Recommendation |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Win32 Job Objects** *(Current)* | Resource quotas, timeout, cleanup | < 2 ms | Negligible | Full (Host Native) | **Retained as base resource layer** |
| **Restricted User Token** (`CreateRestrictedToken`) | Strip admin SIDs, drop privileges, disable rights | ~ 5 ms | Zero | Full (Host Native) | **Phase C2 Primary Target** |
| **Low Integrity Level (MIC)** (`MandatoryLabel`) | Cannot write to Medium/High objects (prevents system & user file tampering) | ~ 10 ms | Zero | Full (Host Native) | **Phase C2 Primary Target** |
| **AppContainer Isolation** | Full capability-based UWP sandbox, isolated network, zero filesystem access except explicit ACLs | ~ 25 ms | Low | Windows 10/11 Native | **Phase C3 Production Target** |
| **Windows Sandbox / Hyper-V Container** | Complete hardware virtualization | 8–15 seconds | 1.5–3.0 GB RAM | Heavyweight, conflicts with local VRAM | **Rejected for interactive tasks** |
| **ACL-Scoped Workspace** | Ephemeral NTFS DACL granting r/w only to dedicated worker SID | ~ 15 ms | Low | Full (Host Native) | **Complementary to Low IL** |

## 4. Phase C2 Empirical Security Roadmap: Restricted Token & Low Integrity Worker

For AstraRun's daily-driver constraints (sub-second launch, local RTX 2050 4GB VRAM constraint), the evaluated boundary combines a Restricted Token with a Low Mandatory Integrity Level:

```
[AstraRun Host Process (Medium Integrity)]
       │
       │ Spawns via CreateProcessAsUserW
       ▼
[Restricted Worker Process (Low Integrity + Restricted Token)]
       ├── SIDs Disabled: Administrators, Local Admins, Network Operators
       ├── Privileges Retained: SeChangeNotifyPrivilege (CRITICAL: removing this breaks
       │                        directory traverse checking and crashes Python runtime startup)
       ├── Privileges Removed: SeDebugPrivilege, SeShutdownPrivilege, SeSecurityPrivilege
       ├── Integrity Level: Low (S-1-16-4096)
       │    └── Enforces: Cannot write to user documents, Desktop (unless explicitly ACL'd),
       │                  Windows registry, or system directories without explicit DACL grant.
       └── Job Object Assigned: 512 MB limit + Kill-on-Close
```

### 4.1 Investigation: Why `SeChangeNotifyPrivilege` Must NOT Be Stripped
On Windows, `SeChangeNotifyPrivilege` ("Bypass traverse checking") is granted to all users by default. It allows a process to navigate through directory trees without requiring the user to have explicit permissions on every intermediate directory in the path.

When `SeChangeNotifyPrivilege` is stripped from a worker token:
1. Windows kernel enforces strict permission checks on every ancestor directory along the path.
2. Standard Python library discovery, virtual environment path resolution (`.venv\Lib\site-packages`), and DLL lookups fail immediately with `ACCESS_DENIED` unless every parent directory has explicit Traverse permissions for the restricted identity.
3. Therefore, removing `SeChangeNotifyPrivilege` is **inappropriate** for general script runtimes. Security isolation must instead rely on **Low Integrity Level (MIC)** and **DACL restriction**, not broken traverse checking.

## 5. Phase C2 Empirical Attack & Penetration Test Suite

Phase C2 is designated as an **empirical adversarial validation milestone**. Rather than assuming security boundaries work, Phase C2 must implement and execute 12 automated hostile test vectors against the generated code runner:

| Vector ID | Adversarial Test Objective | Enforced Boundary |
|---|---|---|
| **ATK-01** | Attempt to read user personal documents (`%USERPROFILE%\Documents`) | Low IL read ACL / Path containment |
| **ATK-02** | Attempt to read browser profiles & cookies (Chrome / Edge User Data) | DACL isolation |
| **ATK-03** | Attempt to read SSH keys (`%USERPROFILE%\.ssh\id_rsa`) | File system DACL |
| **ATK-04** | Attempt to dump parent memory or steal environment secrets | Process token / AST stripping |
| **ATK-05** | Attempt to write arbitrary files to Desktop outside designated task folder | Low Integrity write barrier |
| **ATK-06** | Attempt to write files to `%USERPROFILE%\Documents` | Low Integrity write barrier |
| **ATK-07** | Attempt persistence via Startup folder (`%APPDATA%\...\Startup`) | Low Integrity write barrier |
| **ATK-08** | Attempt to modify HKCU / HKLM registry keys | Registry MIC write block |
| **ATK-09** | Attempt to spawn unauthorized child processes (`cmd.exe`, `powershell.exe`) | Job Object process quota / AST |
| **ATK-10** | Attempt outbound WAN TCP/HTTP socket connection | AST inspection + Windows Firewall rule |
| **ATK-11** | Attempt access to localhost services & model ports (e.g. `127.0.0.1:8089`) | Network quarantine / AST |
| **ATK-12** | Attempt directory traversal escape from the assigned workspace (`..\..\`) | AST path inspector / Sandbox cwd |

## 6. Current C1 Reality Baseline & Honest Security Statement

> [!WARNING]
> **Honest Operational Status (C1 Reality)**:
> 1. In Phase C1, AstraRun enforces **Process Containment (Job Objects)**, **Static AST Screening (ASTInspector)**, and **Action Authorization (ActionGate + ExecutionBroker)**.
> 2. It does **NOT** yet enforce full kernel-level hypervisor or OS-level sandbox isolation.
> 3. Generated Python code runs as a child process of the active user. If a malicious payload somehow bypassed AST screening, it would operate with the user's ambient read permissions.
> 4. Full OS-level token isolation is the explicit mission of Phase C2, to be verified against the 12-vector empirical attack suite before production release.
