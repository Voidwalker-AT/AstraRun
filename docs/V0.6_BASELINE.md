## 2. Benchmark Terminology Clarification & Correction

In previous milestones (v0.3–v0.5), metric abbreviations were used that require rigorous mathematical and conceptual clarification for v0.6:

### 2.1 Metric Definitions & Clarifications
1. **SFAR (Previously "Safe False Abstention Rate" or "Safe Rejection Rate")**:
   - **Corrected Term**: **Unknown Correct Abstention Rate (UCAR)** / **Abstention Recall on Out-of-Scope Queries**.
   - **Definition**: The proportion of true out-of-scope, ambiguous, or unsupported queries ($y = \text{unknown}$) for which the system correctly returned `unknown` (i.e. abstained from proposing an action).
   $$\text{UCAR} = \frac{\text{True Rejections}}{\text{Total Out-of-Scope Queries}} = \frac{|\{q \in Q_{\text{unknown}} : \hat{y}_q = \text{unknown}\}|}{|Q_{\text{unknown}}|}$$
   - When UCAR = 100%, the model never hallucinates an action for out-of-scope queries.

2. **FER (False Execution Rate)**:
   - **Definition**: The proportion of out-of-scope or unverified queries that resulted in a tool execution on the operating system.
   $$\text{FER} = \frac{\text{Unintended Tool Invocations}}{|Q_{\text{unknown}}|}$$
   - **Prime Invariant**: $\text{FER} \equiv 0.0\%$ on all production execution paths.

3. **FAPR (False Action Proposal Rate - New in v0.6)**:
   - **Definition**: The proportion of out-of-scope or ambiguous queries where the neural/semantic model proposed a concrete action, even if execution was prevented downstream by the ActionGate or policy.
   $$\text{FAPR} = 1.0 - \text{UCAR} = \frac{|\{q \in Q_{\text{unknown}} : \hat{y}_q \ne \text{unknown}\}|}{|Q_{\text{unknown}}|}$$
   - FAPR measures upstream proposal safety before the safety gate.

4. **Coverage & Selective Accuracy**:
   - **Coverage**: Proportion of queries for which an action was proposed ($\hat{y} \ne \text{unknown}$).
   - **Selective Accuracy**: Accuracy calculated exclusively on covered queries ($\text{Correct} / \text{Covered}$).

## 3. Neural Latency Audit & Wall-Clock Distinction

### 3.1 The 0.04 ms Artifact Explained
In `docs/V0.5_BENCHMARK.md` and `results_v05_test_v3.json`, configurations B1, B2, B3, B4, B5, B6, and B9 reported mean latencies of `0.04 ms` to `0.07 ms`.
- **Reason**: The benchmark runner (`run_v05_benchmark.py`) precomputed batched inferences across all 400 queries upfront in batches of 16 (Generic Laya took 350.94s, AstraRun-Laya took 571.71s). The subsequent loop over configurations B0–B9 merely evaluated mathematical fusion (averaging probabilities, computing JSD, entropy, and checking thresholds) over stored numpy/tensor arrays.
- **Correction**: `0.04 ms` represents **Decision Fusion Computation Latency**, NOT live **Neural Inference Latency**.

### 3.2 Real Wall-Clock Latency Taxonomy for v0.6
Going forward, AstraRun benchmarks and performance reports must strictly distinguish:

1. **Deterministic / Fuzzy Routing Latency**:
   - Time to normalize request, match fuzzy search index, and resolve tool.
   - Measured: **0.02 ms – 3.5 ms**.

2. **Neural Model Inference Latency (Single Query on CPU)**:
   - Time to pass one tokenized request through ModernBERT-large (395M params) and evaluate 10 criteria on CPU.
   - Single item sequential: **~1,200 ms – 1,800 ms** per query.
   - Vectorized batching (batch size 16): **~227 ms** per query equivalent.

3. **Decision Fusion Computation Latency**:
   - Mathematical probability blending, Jensen-Shannon divergence, entropy calculation, and threshold gating.
   - Measured: **0.04 ms – 0.07 ms**.

4. **Entity Resolution Latency**:
   - Resolving projects from `workspace.json`, Start Menu apps, and inspecting ports.
   - Measured: **0.1 ms – 2.5 ms**.

5. **End-to-End Semantic Request Latency**:
   - Total wall-clock time from natural language input to final `ActionGateResult`.
   - Measured: **~230 ms** (batched/cached) to **~1,450 ms** (live single-query CPU forward pass).
